\section{Firmware}
\label{sec:firmware}

The firmware decides which drives the hardware applies and what the readings mean. It is written in Rust \cite{rust2026} on the asynchronous Embassy framework \cite{embassy2026}, so measurement, USB and WiFi run as concurrent tasks on the RP2350 of the Pico~2~W \cite{rpi2026rp2350, benson2026expad}. On the host computer, 52 tests drive the hardware-independent library against a simulated star network and a simulated jack in simulated time; they caught, for example, swapped high and low drives in the port from the simulator \cite{benson2026topologysim} before the code ran on the hardware.

One \emph{jack monitor} per jack runs the stages of \cref{fig:firmware-overview}: rail measurement and plug detection, identification by solves, and following, with two ways back. The monitor never touches the hardware: it hands out one reading at a time, as drives and the contact to read, and takes the voltage back, so a scheduler can interleave the jacks of both ADCs. \Cref{fig:jack-monitor-states} shows the full state diagram, explained in \cref{sec:appendix-firmware}.

The target of 50 to 100 updates per second and jack was set in the discussion after milestone~1; at \qty{100}{\hertz}, the interval stays below \qty{10}{\milli\second}, the bound commonly given for the latency between a gesture and its audible result \cite{wessel2002problems}. The first firmware solved every jack in turn and reached 2.6 updates per second: each of the nine readings per jack changed the channel of the ADC, and the sinc\textsuperscript{3} filter of the AD7718 needs three conversion periods to settle after a change \cite{adi2001ad7718}, \qty{10.2}{\milli\second} at \qty{315}{\hertz}. Two steps fixed this. First, readings were made faster: a characterization of every filter rate (\cref{tab:adc-characterization}) selected \qty{819}{\hertz}, 2.3 times faster at a noise of \qty{0.39}{\milli\volt}, which the tolerances round up to $\sigma_V = \qty{0.5}{\milli\volt}$. The noisier readings exposed the poorly conditioned solve of a wiper on the tip and raised the minimum conditioning to 0.5. Second, fewer readings are taken: an identified pedal is followed with one reading, and an empty jack costs one plug check every \qty{50}{\milli\second}. Both ADCs convert in parallel, each serving its most overdue jack.

The position is stretched from the range set for the jack to $u \in [0, 1]$, inverted if set, and bent by the drive curve $y = (1+b)\,u/(1 - b + 2bu)$ with $b = 0.9\,d$ for a setting $d \in [-1, 1]$. This is Schlick's bias function \cite{schlick1994bias}, which keeps both ends fixed and gives the inverse curve for $-d$, so it straightens logarithmic and antilogarithmic potentiometers alike. The adapter is a class-compliant USB MIDI device \cite{usbif1999midi} that sends 7-bit control changes, on controller 11 (expression) or 1 (modulation) by default \cite{midi2026controlchange}, once a value differs from the last one by more than 0.6 steps. During development, the adapter froze when connected to a macOS host, likely because the USB driver of embassy-rp 0.10 keeps a suspend latched before the bus reset and then ignores the host \cite{embassy2026pr6693, embassy2023issue1663}. The firmware therefore wraps the driver, clears the stale suspend and ends transfers once the host disconnects, where the driver would otherwise wait forever \cite{embassy2024issue3426}. A WiFi access point with a captive portal serves the web interface, which shows the network of each jack and holds the settings, not yet stored in flash memory.
